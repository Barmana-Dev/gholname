# شواهد پیاده‌سازی صفحه ۲۰

مبنای تطبیق، صفحه ۲۰ فایل «طرح توجیهی کارگزاری ثبتی» و بخش‌های «۱۳-۳ امنیت فنی» و «۱۴-۱ اصول اتصال API» است. فایل ممیزی اصلی تغییر نکرده است.

## کنترل‌های نرم‌افزاری تکمیل‌شده

- دسترسی ارسال API با قابلیت مستقل `registry.enqueue` فقط برای مدیر عملیات و مدیر سامانه و دسترسی مشاهده با `registry.read` برای نقش‌های نظارتی/فنی مجاز اعمال می‌شود؛ ناظر فقط‌خواندنی است.
- Test و Production آدرس و توکن مستقل دارند. Production بدون HTTPS، آدرس و توکن اختصاصی fail-closed است و حالت غیرفعال هیچ درخواست ساختگی تولید نمی‌کند.
- صف تنها پرونده موجود در وضعیت `registry_exchange` و خدمت فعال دارای `api_code` را می‌پذیرد. payload ورودی کاربر پذیرفته نمی‌شود؛ داده از پرونده ساخته و فقط مسیرهای whitelist شده در `api_payload_fields` ارسال می‌شود.
- کلید idempotency، request ID، محیط، وضعیت، تعداد تلاش، زمان پاسخ، کد وضعیت، outcome، کد خطا و SHA-256 درخواست/پاسخ ثبت می‌شوند. متن پاسخ حساس ذخیره نمی‌شود.
- payload صف با AES-256-GCM رمز و با SHA-256 کنترل تمامیت می‌شود. پاسخ بیش از ۱ MiB رد می‌شود، timeout پانزده ثانیه است، retry نمایی، بازیابی job قفل‌مانده و dead-letter همراه رخداد امنیتی فعال است.
- UI مدیریت خدمت امکان تعیین کد API و whitelist فیلدهای سند هر خدمت را دارد؛ UI عملیات فقط در وضعیت مجاز دکمه ارسال را نمایش می‌دهد و داشبورد صف محیط و پرونده را بدون نمایش کلید idempotency نشان می‌دهد.

## مرز زیرساختی

HTTPS لبه، فایروال، محدودیت دسترسی میزبان، اجرای زمان‌بندی‌شده اسکن/backup، آزمون نفوذ مستقل و کلید/سند رسمی سازمان ثبت خارج از کد محلی هستند. اتصال در نبود این تنظیمات عمداً متوقف می‌ماند.

## آزمون‌ها

- `server/src/registry-integration.test.ts`: کمینه‌سازی payload، جلوگیری از prototype pollution، hash تمامیت و طبقه‌بندی خطای upstream.
- `server/src/security-features.test.ts`: مجوز ارسال مدیر عملیات، منع ارسال ناظر و مشاهده فقط‌خواندنی ناظر.
