# شواهد پیاده‌سازی الزامات نرم‌افزاری صفحه ۳

منبع بررسی: صفحه ۳ فایل «طرح توجیهی کارگزاری ثبتی (1).pdf»، فصل ۴ (اهداف اصلی طرح) و فصل ۵ (ضرورت‌های حاکمیتی، اجتماعی و اقتصادی).

## تطبیق الزامات نرم‌افزاری

| الزام صفحه ۳                                        | شاهد اجرایی                                                                                                                                           |
| --------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| سامانه غیرحضوری و تبادل برخط با سازمان ثبت          | مسیرهای عمومی و پنل React، APIهای Express، صف تبادل دارای شناسه درخواست و idempotency؛ فعال‌سازی تبادل واقعی منوط به API رسمی سازمان است.             |
| حداقل سه خدمت اولیه                                 | خدمات ثبتی و فرم‌های اختصاصی با اعتبارسنجی سمت UI و API در ساختار موجود ارائه شده‌اند.                                                                |
| پاسخ‌گویی، پشتیبانی، کنترل کیفیت و مدیریت پرونده    | تیکت، پیام پرونده، تعامل تلفنی/ایمیل/چت/حضوری، امتیاز کیفیت، گردش وضعیت و ارجاع نقش‌محور در API و UI موجود است.                                       |
| کارشناسان ثبتی، حقوقی و نقشه‌برداری                 | نقش‌های مجزا، دسترسی فقط به پرونده ارجاع‌شده و گزارش تخصصی متناسب با نقش در API اعمال می‌شود.                                                         |
| کنترل تخلف، جعل، سوءاستفاده، وجه غیرمجاز و محرمانگی | ارزیابی ریسک، رخداد امنیتی، طبقه‌بندی مدرک، هشدار پرداخت رسمی، رمزنگاری داده حساس، ثبت audit و کنترل دسترسی اعمال شده است.                            |
| معماری امن، قابل بازرسی و قابل پایش                 | Helmet، CORS محدود، rate limit، JWT، MFA، RBAC/capability، زنجیره hash در audit، شاخص‌های سلامت و منابع و رخدادهای سامانه موجود است.                  |
| مرکز تماس تلفنی و آنلاین                            | ثبت تعامل چندکاناله و مرکز تیکت آنلاین آماده است؛ اتصال مخابراتی واقعی به تأمین‌کننده رسمی وابسته است.                                                |
| داشبورد نظارتی فقط‌خواندنی سازمان ثبت               | نقش `observer` در UI فقط سطوح مشاهده را دریافت می‌کند و middleware مشترک API تمام POST/PATCH/PUT/DELETE این نقش را پیش از منطق مسیر با 403 رد می‌کند. |

موارد شعبه فیزیکی، معرفی اشخاص دارای صلاحیت، مجوزها، آزمون نفوذ رسمی، اینماد، پروانه کسب، میزبانی داخلی و SLA قراردادی خارج از کدنویسی و وابسته به مدارک و ارائه‌دهندگان رسمی هستند.

## آزمون مرتبط

- `server/src/read-only-observer.test.ts`: اثبات دسترسی GET/HEAD/OPTIONS و رد قطعی POST/PATCH/DELETE برای ناظر.
- `server/src/security-features.test.ts`: اثبات نبود قابلیت‌های مدیریتی و شکایت برای ناظر.
- `client/src/access.test.ts`: اثبات عدم نمایش سطوح قابل‌نوشتن شکایت و پشتیبانی برای ناظر.
